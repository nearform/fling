# Deploying Fling

Fling runs serverless in the Nearform Labs AWS account (eu-west-1 plus global
CloudFront). The infrastructure is Terraform in
[nearform/labs-infra](https://github.com/nearform/labs-infra): `envs/production/app-fling.tf`, using
`modules/serverless-static-app`. This repository ships the code.

```
fling.labs.nearform.com    CloudFront ─┬─ /api/*, /auth/*, /healthz,
                                       │  /mcp, /oauth/*, /.well-known/* → Lambda labs-production-fling-api (function URL)
                                       └─ everything else          → S3 nearform-labs-production-fling-ui (SPA)
*.fling.labs.nearform.com  CloudFront ── site router (CloudFront Function + KeyValueStore)
                                       └─ S3 nearform-labs-production-fling-sites
DynamoDB labs-production-fling, SSM parameters /labs/production/fling/*
```

| Who | Owns |
| --- | --- |
| labs-infra (Terraform) | Buckets, table, distributions, DNS, certificate, roles, the function's configuration and environment, which secrets exist |
| This repo, `deploy.yml` | The Lambda code, the UI files, `downloads/fling.mcpb` in the UI bucket, `_fling/404.html` in the sites bucket, the site router's code |
| The API at runtime | Table items, KeyValueStore keys, site files under `sites/`, chunked MCP upload staging under `uploads/` |

The remote MCP connector (`/mcp`, OAuth under `/oauth/*` and `/.well-known/oauth-*`) needs, beyond
the routes above: DynamoDB TTL enabled on the attribute `ttl` (OAuth codes, requests, refresh
tokens, grants, DCR clients and uploads carry it), the function role allowed to `s3:PutObject`,
`s3:GetObject` and delete/list under `uploads/*` as well as `sites/*`, and ideally a lifecycle rule
expiring `uploads/` after a day. `/mcp` requests carry whole sites, so CloudFront must forward
`POST` bodies up to the Lambda limit (6 MB) and the `Authorization`, `Mcp-Protocol-Version` and
`Accept` headers. Access tokens are signed with a key derived from `SESSION_SECRET` (HKDF), so no
new secret is needed; rotating `SESSION_SECRET` invalidates live access tokens (clients just refresh;
refresh tokens are opaque and stored hashed). `OAUTH_REDIRECT_ALLOWLIST` (optional) overrides the allowed OAuth redirect URIs.

## One-time setup

1. **Infrastructure.** Merge the labs-infra pull request that adds `app-fling.tf`. Its CI applies it.
   Before merging, once this repository exists, set its numeric id in `app-fling.tf`
   (`repo_id`, from `gh api repos/nearform/fling --jq .id`). Until then no workflow can assume the deploy role.

2. **Google sign-in secrets.** Fling reuses Agentic Mapper's Google OAuth client. From a labs-infra
   checkout, with your own SSO credentials:

   ```bash
   aws sso login
   terraform -chdir=envs/production init
   scripts/fling-copy-google-secret.sh production
   ```

   It copies `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` from Secrets Manager
   `labs/production/agentic-mapper/app` into SSM `/labs/production/fling/google-client-id` and
   `google-client-secret`. The other secrets (`session-secret`, `site-hmac-key`,
   `origin-verify-secret`) are generated by Terraform.

3. **Google redirect URIs.** In Google Cloud Console, open Agentic Mapper's OAuth client
   (APIs & Services, Credentials) and add these authorised redirect URIs:
   - `https://fling.labs.nearform.com/auth/google/callback`
   - `http://localhost:3001/auth/google/callback` (local development)

4. **GitHub environment and config.** In this repository, create the environment `production`
   (Settings, Environments; deployment branches: `main` only). Then set the deploy config from the
   Terraform output:

   ```bash
   terraform -chdir=envs/production output -json fling | jq -c .deploy \
     | gh variable set AWS_DEPLOY_CONFIG -R nearform/fling
   ```

   It holds `AWS_REGION`, `AWS_DEPLOY_ROLE_ARN`, `LAMBDA_FUNCTION`, `UI_BUCKET`, `SITES_BUCKET`,
   `SITE_ROUTER_FUNCTION`, `APP_DISTRIBUTION_ID`, `SITES_DISTRIBUTION_ID` and `APP_ORIGIN`. Nothing in
   it is secret.

5. **npm publish token.** Repository secret `NPM_PUBLISH_TOKEN`: a token that can publish
   `@nearform/fling` (only `release-cli.yml` uses it). Every dependency is public, so installs
   need no token.

6. **First deploy.** Push to `main`, or run the Deploy workflow by hand. Until then the API answers
   503, the UI bucket is empty and the site router passes requests straight through.

## How a deploy ships

Every push to `main` runs `ci.yml` (`pnpm gate`). When it passes, `deploy.yml` builds the same commit
and, with the deploy role over OIDC:

1. Uploads `apps/api/dist/lambda.zip` to the function and waits until it is live.
2. Syncs `apps/web/dist` to the UI bucket: `assets/` first (hashed, cached for a year, never deleted,
   so open tabs keep working), then the other files, then `index.html` (`no-cache`) last.
   It also uploads the Claude Desktop extension, built by `pnpm --filter @nearform/fling build:mcpb`,
   to `downloads/fling.mcpb`: `application/octet-stream`, served as an attachment, 5-minute cache.
   The UI sync excludes `downloads/*` so it doesn't delete the extension. The file has an extension,
   so the SPA function leaves it alone and it is served at
   `https://fling.labs.nearform.com/downloads/fling.mcpb`.
3. Uploads `apps/web/dist-404/404.html` to `s3://<sites bucket>/_fling/404.html`. The sites
   distribution answers every S3 403 or 404 with it, as a 404.
4. Fills `__APP_ORIGIN__` and `__SITE_SCHEME__` in `edge/src/site-router.js`, updates the CloudFront
   Function (keeping its KeyValueStore association) and publishes it to LIVE.
5. Invalidates `/index.html` on the app distribution and `/_fling/*` on the sites distribution.

Site content is never touched by a deploy. Terraform ignores the code, so a labs-infra plan after a
deploy reads "No changes".

## Rollback

Run the **Deploy** workflow by hand (Actions, Deploy, Run workflow) with `ref` set to an older commit
SHA of `main`. It rebuilds and redeploys that commit: API, UI, error page and site router together.
Old UI assets are still in the bucket, so nothing breaks while it runs.

Table items and KeyValueStore keys are not rolled back. Keep the data model backwards compatible, or
roll forward. A single site rolls back with `fling rollback <name> <versionId>`.

## Releasing the CLI

Bump `apps/cli/package.json`, merge, then tag that commit:

```bash
git tag cli-v0.2.0 && git push origin cli-v0.2.0
```

`release-cli.yml` checks the tag matches the version, runs the gate and publishes `@nearform/fling` to
npm with provenance.

## Secrets

SSM SecureString parameters under `/labs/production/fling/`, read by the function at cold start:

| Parameter | Source |
| --- | --- |
| `google-client-id`, `google-client-secret` | `scripts/fling-copy-google-secret.sh` in labs-infra |
| `session-secret`, `site-hmac-key` | Generated by Terraform, never in its state |
| `origin-verify-secret` | Generated by Terraform. CloudFront also sends it to the function URL as `X-Origin-Verify` |

To rotate the generated ones, bump `secrets_version` in `app-fling.tf` and merge, then redeploy so
warm functions pick them up. Rotating `session-secret` signs everyone out. Rotating `site-hmac-key`
also needs the copy the site router reads from the KeyValueStore updated by the API.

## Deploy security (public repository)

- **No AWS keys in GitHub.** The deploy job assumes the app's deploy role over OIDC. The role trusts
  only this repository's `production` environment, and that environment only accepts deployments from
  `main` (a deployment branch policy).
- **Deploys only run code from `main`.** They run after CI passes on a push to `main`, or by hand with
  a `ref` that must be on `main` (checked with `git merge-base --is-ancestor`). Pull request runs,
  including forks', never get the role or any secret.
- **The deploy role can't read app secrets.** It can update the Lambda code, the UI bucket,
  `_fling/*` in the sites bucket and the CloudFront functions, and invalidate caches. Google
  credentials and the signing keys live in SSM, readable only by the Lambda's own role.
- **Logs are public.** They show resource names and the role ARN, which are identifiers, not
  credentials. Never `echo` anything secret in a workflow.
- Anyone who can push to `main` can deploy. Protect `main` (require pull requests) to tighten
  this.

## Costs

About $0 when idle. Lambda, CloudFront (PriceClass_100), DynamoDB on demand, the KeyValueStore,
CloudFront Functions and standard SSM parameters cost nothing or pennies at internal scale. The ACM
certificate is free. The only steady cost is S3 storage of site versions, about $0.023 per GB-month.
Logs are kept for 30 days.
